Primary "genuinely separate machine" evidence for #709, addressing review
feedback that a host->guest KVM matrix (client = the physical Proxmox host
itself) doesn't satisfy "cross-machine client using the same path that
reproduced #708". Per explicit instruction, only `ssh proxmox` was used --
no other LAN host was touched for this evidence.

Two disposable LXC containers were created directly on the Proxmox host
(`pct create`), each a separate network namespace/process reached only via
`ssh proxmox` (no other physical machine involved):

  SUT (VMID 106, "tardi709-sut"):    192.168.86.56, 4 cores, 2048MB
  Client (VMID 107, "tardi709-client"): 192.168.86.59, 2 cores, 1024MB

Both from local:vztmpl/debian-13-standard_13.1-2_amd64.tar.zst.
Tardigrade cross-compiled locally (zig build -Doptimize=ReleaseFast
-Dtarget=x86_64-linux-gnu) at commit a81cfcdc5ab1ffc801493c8792bde9f3c2786425
(the exact PR head at diagnosis time), binary SHA-256
ac31a48ff524f8e12d90590445b03090750788b843c6146cfeafd4c7d722bdee, copied
into the SUT container. wrk installed via apt inside the client container.
Origin fixture (benchmarks/fixtures/upstream_server.py) local to the SUT on
127.0.0.1:18080, matching the #708/#593 policy of keeping the proxied
origin local to the SUT.

All rows: `wrk -t4 -c32`, TARDIGRADE_RATE_LIMIT_RPS=0, /proxy/health.
Between churn-heavy rows, ss -tan state time-wait was polled on the client
until it dropped below 50 before starting the next row, to avoid one row's
leftover TIME_WAIT population contaminating the next (an early attempt at
this matrix without draining showed exactly that contamination -- see
REPORT.md's discussion).

Caveat this evidence does NOT resolve: both containers still share the same
physical CPU/kernel/network stack as the Proxmox host (LXC, not separate
hardware) -- this is a real network hop between two separate kernel
namespaces/processes/IPs, not a hairpin loopback, but it is still not
literally two distinct physical machines the way the original #708
MacBook->KVM-guest reproduction was. Treat this as the best available
"genuinely separate client" evidence obtainable through the sanctioned
`ssh proxmox`-only workflow, not as a claim of full physical-network
reproduction.

Containers destroyed (pct stop / pct destroy --purge) after artifacts were
pulled, matching the ephemeral-resource convention used elsewhere in this
diagnosis.
